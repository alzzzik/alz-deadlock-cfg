# CPU-side (fight-time) ConVar levers for Deadlock that keep the game looking good

Scope: `ConVars` block of `gameinfo.gi` only, Ryzen 7 5700X (8c/16t Zen 3, one CCD, all cores identical), RTX 5070, CPU-bound in team fights. Baseline config: `/home/user/alz-deadlock-cfg/experimental/gameinfo.gi` (liv's compylock + round 2/3). Findings already in `/home/user/alz-deadlock-cfg/RESEARCH.md` are not repeated except where this note corrects or sharpens them.

Data freshness: Valve's convar dump and stock files were re-pulled from SteamDatabase at **build 6785 (commit 4e0f960, 2026-10-15)**, which is newer than the DMM catalogue (convar build 6769) used by earlier research. Diff 6769 → 6785: **no new `gameinfo_cannot_override` flags (still 124), no removals, 4 new convars**, one of which is a real CPU/GPU lever (`r_citadel_disable_particle_lights`, see Q1). Flag reading used below: `gamedll` without `clientdll` = server module only (no effect online); `replicated` = server value wins online; `developmentonly` = only settable from `gameinfo.gi`/startup; `release` = can be A/B tested live in the console; `archive` = a saved user value can override `gameinfo.gi`; `cheat` = applies from `gameinfo.gi` at startup (per earlier research).

## Q1. Which CPU-side convars NOT yet in the experimental config have evidence of improving fight-time FPS / 1% lows without visual loss?

### Takeaway
There is exactly one genuinely new lever with strong provenance: **`r_citadel_disable_particle_lights true`**, a `release` convar added after build 6769 and present in 6785, which the OptimizationLock author says a Valve developer pointed him to, right after Valve said it would ship "performance-related ConVars" to compensate for blocking the lighting convars. It is untested publicly (no FPS numbers) but is the best candidate to A/B live in the console. Almost everything else not yet in the config is either already Valve-default/stock, server-only, replicated, hides information, or has no evidence at all.

### Inferences
- Particle lights are dynamic lights spawned by ability effects; with `lb_enable_dynamic_lights` now blocked, they are the remaining fight-scaling light load. They cost GPU shading and some CPU (light setup/binning per frame), so on a CPU-bound 5700X the gain is plausible but unproven; the `release` flag means it can be toggled mid-fight in the console (`r_citadel_disable_particle_lights 1` / `0`) for a quick A/B before committing it to `gameinfo.gi`. Visual cost is a "flatter" look of ability glows, not hidden information, so it fits the "looks decent" target better than any blocked lighting convar did.
- The headroom left in the ConVars block for CPU work is small. The engine already defaults every multithreading switch on, and Valve's stock tail sets the parallel/partition lines itself; the remaining CPU levers are particle-side (fallbacks, particle lights) and the "do less" levers that hide things (excluded).

### Gaps
- No measured FPS/1% low numbers exist anywhere for `r_citadel_disable_particle_lights` (forums.playdeadlock.com was unreachable from this session; the Valve-dev forum reply was only seen secondhand via issue #88).
- Exact build that introduced `r_citadel_disable_particle_lights` (between 6769 and 6785) could not be pinned without the GitHub API.

## Q2. Are the CPU values already in the config well-chosen for an 8-core Zen 3? Any evidence some hurt?

### Takeaway
Nothing in the CPU block has measured evidence of hurting *except* the five lines round 3 already reset. But several "CPU" lines are no-ops or mis-aimed: `thread_pool_option 2` does nothing on a non-hybrid CPU, `r_update_particles_on_render_only_frames true` targets a special engine mode and is not a saver, two settings are silently duplicated by Valve's stock tail later in the same block (`sc_layer_batch_threshold_fullsort` 120 vs 20, `snd_ui_positional` false vs 1), and `snd_mixahead 0.05` buys no proven CPU but adds audio latency. The particle fallback settings work as designed and are the right kind of lever; the earlier suspicion that they hide the headshot particle is wrong.

### Inferences
- **Fallbacks at 1 ms / 100 / 5 / 10 are fine on a 5700X.** A 1 ms threshold means fallbacks engage in essentially every fight, but they only ever swap to Valve-authored cheaper versions (systems without an `m_hFallback` are untouched), so this is a "looks a bit simpler under load" lever, not a "hides effects" lever. If any specific ability looks wrong, the middle ground ghempy53 used (2 ms / 20 / 2 / 5) is the fallback.
- **`r_particle_model_per_thread_count 64` may be slightly wrong for 16 threads.** If it is the batch size per particle-model job (the only reading the name supports), doubling it halves the number of jobs, which reduces scheduling overhead but also reduces how many of the 5700X's 16 threads can share a fight's particle-model work. With no data either way, Valve's 32 is the safer default on a many-thread CPU; it is a cheap single-variable A/B.
- **`r_update_particles_on_render_only_frames true` is not a saver.** If "render only" is the engine mode used during saves/loads (as the `autosave_fully_async` help states), the line is a no-op in matches; if it ever applies, `true` means *more* particle updates. Either way it cannot raise FPS. Reset to default.
- **The duplicated keys need a 10-second console check.** Whichever occurrence the KeyValues loader keeps, one of the two authors' intentions is silently lost. Typing `sc_layer_batch_threshold_fullsort` and `snd_ui_positional` in the console shows which won; then delete the losing line. Given round 3's experience with the other two batch thresholds, Valve's stock 20 is the safer value to keep.
- **`snd_steamaudio_num_threads 6` likely creates idle threads** (reflections/reverb/pathing are off in stock), so it gains nothing and is not worth keeping; `2` (Valve) is the clean value.
- **`snd_mixahead 0.05` is a gameplay cost with no shown benefit.** Fifty milliseconds of audio buffering delays footstep/ability cues relative to the picture; revert to 0.001 unless an A/B shows a CPU win. Because it is `archive`, check the live value in the console anyway.
- **`engine_max_ticks_to_simulate 2`** only matters when one frame takes longer than two 64-tick intervals (>31 ms, i.e. <32 FPS). It neither helps nor hurts normal fight FPS; keep or remove purely on camera feel.
- **Valve's stock-tail lines** (`cl_interp_parallel 1`, `iv_parallel_restore 1`, the spatial-partition and `parallel_perform_invalidate_physics` lines, `cl_aggregate_particles`, `r_particle_batch_collections`) are Valve's own tuned values for this game. They are correct for any core count and should not be "tuned" further.

### Gaps
- No source states whether Source 2's `gameinfo.gi` ConVars loader keeps the first or last duplicate key; needs an in-game console check.
- No measured A/B exists for `r_particle_model_per_thread_count`, `r_strip_invisible_during_sceneobject_update`, `r_particle_skip_postsim`, `cl_simulate_dormant_entities` or `engine_max_ticks_to_simulate` on any hardware; all evidence is "set by N configs".
- The exact meaning of "render only frames" for particles is inferred from neighbouring Valve help text, not documented directly.

## Q3. What does `thread_pool_option` actually do (values -1, 0, 1, 2)?

### Takeaway
It is the engine's **CPU core-type preference for the job thread pool on hybrid CPUs** (Intel P-cores/E-cores). In CS2 (same Source 2 engine, same `hidden release` convar), Valve exposes it as "CPU Cores Usage Preference": **0 = Performance Cores Only, 2 = Prefer Performance Cores, 3 = No Preference** (1 = presumably Efficiency Cores Only, labelled in localization but not offered). On CPUs that don't report different core types, CS2 hides the option and forces 3. On a Ryzen 7 5700X every core has the same efficiency class, so `-1`, `2` and `3` should all behave the same: **`thread_pool_option 2` is a no-op for this user**, not a performance lever.

### Cited Findings

### Inferences
- `-1` most likely means "use `Engine2/ThreadPoolCoreTypeRequest` from gameinfo or the engine default". Because the 5700X reports one efficiency class for all 8 cores (16 threads), 0/2/3 all map to "all cores", so the line cannot change FPS. Revert to `-1` (or delete it) so the config doesn't suggest a lever that isn't there. `0` ("P-cores only") is the only value with a theoretical risk on odd hardware (if detection misfires); there is no reason to use it.
- The setting is read at startup ("Requires the game to be restarted"), so live console A/B is meaningless even though the flag is `release`.
- Thread-pool size itself is not exposed as a convar (no `job_*`/thread-count convar exists in the 6785 dump); only the `-threads` launch option, which earlier research already rejected for limiting the pool.

### Gaps
- Value `1` = "Efficiency Cores Only" is inferred from the localization string order; the CS2 dropdown never offers it.
- No Deadlock-specific benchmark of any `thread_pool_option` value exists.

## Q4. Which convars are replicated or server-only (no effect online) and should be avoided?

### Takeaway
In the experimental config, 11 active lines are server-module only and 23 are `replicated`; none of them do anything in real matches beyond what Valve's servers already use. The replicated parallel/partition lines are harmless because they are Valve's own stock values. For new candidates, avoid everything `gamedll`-only (`ai_*`, `nav_*`, `minimap_*update_rate_hz`, `citadel_use_pvs_for_players`) and all animgraph/IK/ragdoll-physics tuning (replicated), which is where many "FPS" claims in community configs come from because people test in bot matches.
